## Extraction plan (Rust-estate playbook: pull from consumers, one concern each)

| New kit | Absorbs | Rigor anchor |
|---|---|---|
| `@est/starlight-plugin` | starlight-kit factory + multi-site config merge | zod schema fixtures (one definePlugin, validated config) |
| `@est/content-guard` | content-guard validators (pure functions) | a bad-content fixture corpus (frontmatter/links/math/mdx) |
| `@est/islands` | interactive-islands registry + auto-import | registry fixtures |
| `@est/deploy-targets` | multi-site deploy emitters | emitted-output golden files (cloudflare, GH Actions) |
| `@est/math` | starlight-katex remark + css loader | render fixtures |
| theme tokens | shroom-theme + cross-domain-sync | CSS custom properties generated from the Rust `theme-kit` (one token source, both ecosystems) |

## Dogfood path

The web estate's own docs app (Starlight) is the first consumer:
`@est/content-guard` in its CI is the docs gate for MDX, and the docs
config migrates to `@est/starlight-plugin`. `core` status for each new
kit starts the day the docs app pins it.

## Scope notes

- npm scope migrates `@wyatt/*` to `@est/*` (one convention across the
  web estate; the old names are frozen at 0.1.0 and unpublished).
- `commander`+`picocolors` and `zod` appear in two repos each; the kits
  absorb them as shared dependencies, not per-repo copies.
- `starlight-dse-test` stays a corpus; `nightjar`, `WyattsNotes` are
  content repos, not extraction targets.
