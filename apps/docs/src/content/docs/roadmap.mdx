## Thesis

The Rust estate compounds because kits were extracted from real suites and
`core` is earned by exact consumer pins. The web estate inherits that loop:
each phase exists to produce one deployed suite that pins kits and forces
the next extraction.

## Phase 1: the fetch bridge

`@est/fetchkit` is shipped and fixture-pinned: backoff formula mirrored
from `retry-backoff` (same defaults, same cap, same jitter bound), strict
envelope decoding, status-to-errcode mapping on the wire
(`RATE_LIMITED`, not variant names), loopback integration tests over real
HTTP. Cache semantics are deferred to `@est/cachekit` (SC-1: one concern).

Remaining for exit: a deployed suite performs a live round trip against an
axum backend endpoint speaking envelopes over HTTP (the deployed directory
is live; the backend endpoint is the open decision). Exit: `fetchkit`
eligible for `core`.

## Phase 3: the money-grade suite

`@est/money-wasm`: the `money` crate in the browser, fixtures from the Rust
test vectors, algebra inherited from `accounting-spec`. Consumer: the
**ledger dashboard suite** composing `webauthn-kit`, `money-wasm`,
envelope errors, flags, i18n, `ws`, otel. The suite composes; it holds no
business logic. One suite graduates several kits to `core` at once.

## Phase 4: platform hardening

Shared web CI workflow (the `rust-kit` analog); SBOM and provenance for npm
artifacts; TS semver gate; `OmniWeb-template`; CSS tokens generated from
`theme-kit`; `a11y-kit` checklist on islands; `starlight-kit` consolidation
of the per-site repos.

## Repo lifecycle

Monorepo until a kit gains an external consumer, an independent release
cadence, or CI contention; then extract. The registry schema models both
shapes (`packages:` today, `repos:` when split), so the audit does not
change.

## Standing decisions (2026-11-01)

2. npm posture: **publish `@est/*` publicly at `core` graduation**, mirroring
   the crates.io discipline.
